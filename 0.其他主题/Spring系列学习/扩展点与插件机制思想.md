# 扩展点与插件机制思想（设计思想笔记）

> 来源：2026-09-04 学 Spring AOP 时，把 AOP 类比成「插件机制」后向上抽象出来的思想。
> 它比任何单个框架都通用：从 CPU 中断到 VSCode 插件市场，结构完全同构。

## 一、一句话内核

**把变化点做成参数：稳定骨架 + 抽象契约 + 调用方向倒置。**

| 层次 | 名字 | 含义 |
|---|---|---|
| 目的 | 开闭原则 | 对扩展开放、对修改关闭：不动核心，增量应对变化 |
| 手段 | 控制反转 / 好莱坞原则 | 别打给我们，我们会打给你：流程主人不调用具体逻辑，等逻辑注册后反过来调它 |
| 架构形态 | 微内核 + 插件 | 最小稳定内核 + 满足契约的外部插件 |

## 二、完整公式（比「预留扩展点」多一步）

朴素表述：原始流程提前预留扩展点，外部插件实现对扩展点的增强。这个表述缺了最锋利的一步：

1. **稳定骨架**：固化不变的流程、生命周期、循环结构。
2. **抽象契约**：在「可能变」的位置不写死逻辑，只声明接口 / 注解 / URL。
3. **调用方向倒置**：核心在编译期完全不认识插件；插件满足契约即可被回调。

没有倒置只是 if-else 多分支；有了倒置才是扩展机制。事件发布器、注册表、分发器都是「契约与倒置」的零件，不是思想本身。

## 三、插件五要素与 Spring 对位

插件五要素：扩展点、事件、分发器、注册表、插件。

**对位 AOP（易错版）**：扩展点 = JoinPoint；**事件 = 某方法被调用这件事**（不是 Pointcut）；订阅规则 = Pointcut；**插件本体 = Advice / 切面**（不是代理对象）；注册表 = Advisor 集合（Pointcut 到 Advice 的映射）；**分发器 = 代理内拦截器链**（proceed 递归，不是 Advice）；装载动作 = 织入。

**完美对位 1：Spring 事件机制**。扩展点 = publishEvent 调用点；事件 = ApplicationEvent；分发器 = ApplicationEventMulticaster；注册表 = 容器中的监听器集合；插件 = @EventListener 方法。

**完美对位 2：BeanPostProcessor**。扩展点 = bean 初始化前后；注册表 = 容器持有的 postProcessor 列表；分发器 = 容器遍历调用；插件 = 各 postProcessor 实现。AOP 代理就是这套插件机制长出来的产物。

**与插件机制的两个本质差异**：插件机制需要宿主主动预留钩子（侵入式），AOP 对宿主代码零侵入；插件通常支持运行时插拔，Spring AOP 切面在启动生成代理时就焊死了。

## 四、为什么这么通用（四个根因）

1. 变化是唯一常态：核心要稳、需求狂飙，只有「骨架不动 + 插件增量」同时满足两头。
2. 组合爆炸驯服：m 个方法 x n 个横切需求，直接写是 m x n 份代码，抽成扩展点只需 m + n 份（AOP 的原始动机）。
3. 分工与生态：核心作者无法预见所有需求，开放扩展点等于让全世界替你开发（VSCode 插件市场）。
4. 风险隔离：改核心全量回归，加插件增量验证。

## 五、广度巡礼（换层不换骨）

| 层级 | 实例 | 对位 |
|---|---|---|
| 硬件/内核 | 中断向量表 | 注册表；中断 = 事件，内核 = 分发器，驱动 = 插件 |
| OS | Linux 可加载模块、信号 handler | 内核扩展点 + 驱动插件 |
| 工具链 | git hooks（pre-commit） | 字面意义的生命周期钩子 |
| 语言 | 函数指针、回调、装饰器、高阶函数 | sort(comparator)：排序流程是骨架，比较逻辑是插件 |
| 类库 | Comparator、Stream、JUnit @Before/@After | 测试生命周期钩子 |
| 框架 | Spring 五层（BeanPostProcessor / AOP / Interceptor / EventListener / EnvironmentPostProcessor）、MyBatis 拦截器、Netty pipeline、Servlet Filter | 同一思想换五层皮 |
| 生态协议 | Java SPI（JDBC：DriverManager 注册表 + MySQL 驱动插件） | 插件机制标准化 |
| 云原生 | K8s admission webhook | 请求路径钩子，插件是 HTTP 服务 |
| 互联网 | Webhook | 注册表 = 配置的 URL，分发器 = 平台 POST |
| 产品 | VSCode / Chrome 扩展、Photoshop 滤镜、游戏 mod、微信「分享到」 | 微内核 + 插件市场 |

## 六、滥用边界

不是每个函数都该留钩子。唯一判断标准：**这个位置存在可预见的多变吗？** 只有一种实现且长期不变的逻辑，硬抽接口 + 插件就是过度设计。扩展点的每个空位都是认知税；extension hell 与好设计的差距在业务判断力。

## 七、关联

- AOP = 方法执行路径上的钩子机制（运行时织入、拦截器链）。
- 迷你 IoC 常驻机制 = 阻塞线程续命（另一条线：事件驱动）。
- 手写路线：v2 BeanPostProcessor 亲手实现「注册表 + 分发器」；v3 AOP 从它上面长出。
